# Eva · Supabase (Earth / cloud side)

Supabase replaces the planned Firebase setup (decision: [`docs/app/ADR-014-supabase.md`](../docs/app/ADR-014-supabase.md)). The ship stays offline-first and never talks to Supabase. Supabase holds a **copy** of what the ground node has already verified and acknowledged, plus team data, and serves Eva's web chat.

Project: `eva-wearmeds`, region `sa-east-1` (São Paulo), free plan.

## Layout

| Path | What |
|---|---|
| `migrations/` | SQL migrations, applied in order: roles and profiles, ship data, journal and team, storage, chat rate limit, `public_stats` |
| `tests/rls.test.sql` | RLS and integrity tests (80 checks), one transaction, rolled back |
| `tests/local/` | Run the migrations and tests on a throwaway local PostgreSQL without Docker |
| `functions/eva-chat/` | Edge Function (Deno): JWT check, per-user rate limit, the app's topic guard, Groq |
| `seed.sql` | Demo data (fictional, from `app/src/seed.rs`), generated by `scripts/seed.mjs` |
| `scripts/seed.mjs` | Builds `seed.sql` with hash-chained, Ed25519-signed records (same hashing as `app/src/chain.rs`) |
| `scripts/export-chain.mjs` | Exports a ship's mirrored records to the app's chain format for `eva verify` |
| `scripts/provision.sh` | End-to-end setup of the hosted project (idempotent, prints no secrets) |
| `site/` | `/status/` page and `/api/status` route for the public site (copied there by `provision.sh`) |
| `config.toml` | Supabase CLI config (functions deploy, local `supabase start`) |

## Data model

Translated from the Firebase kit's `DATA-MODEL.md` and `firestore.rules`.

| Table | Contents | Written by |
|---|---|---|
| `profiles` | One per auth user (created by a trigger on sign-up): `display_name`, `email`, `prefs`, `role` (`crew_lead` · `mission_control` · `team` · `viewer`, default `viewer`) | owner (`display_name`, `prefs` only); `role` only by `admin_set_role()` or the service role, audited in `role_changes` |
| `ships` | Ship summary, `demo` flag, pinned Ed25519 `pubkey` (immutable), `epoch` (only moves forward), head | service role; mission control may edit `display_name`, `notes` |
| `records` | Signed chain mirror: `ship, epoch, seq, ts, kind, subject, hash, prev, signature, body` (+ `ground_received_ms`, `ingested_at`). PK `(ship, epoch, seq)` | **service role only, append-only**: triggers refuse UPDATE, DELETE and TRUNCATE for everyone; an insert must link to the previous record's hash (and seq 0 to genesis) |
| `cases`, `case_notes` | Cases rebuilt by the ground; helpers by seat and task, never names. Notes are append-only | service role; notes by mission control / crew lead |
| `passengers` | Triage summary only: `seat, label ("Ana R."), role, trained, grp, status` | service role. Checks refuse full names and free text in `status`; an event trigger (where permitted) and a test refuse vitals-like columns |
| `station_state` | Medical station: mode, 12 compartments. No health data | service role |
| `journal_entries` | Private per user | owner only (nobody else, not even mission control, can read them) |
| `team_docs` | Reports, notes, asset metadata | team, mission control (author or mission control edit / delete) |
| `rate_limits` | eva-chat buckets (6 / min, 80 / day) | only through `eva_chat_consume()` |
| `public_stats` (view) | Per ship: acknowledged record count, last ingest, open / total cases, passenger count, station mode | read by `anon` (the `/status/` page) |

The ground node's ingest (later, `app/src/cloud.rs` as in the Firebase kit's INTEGRATION.md, part A) writes with the service role, using `insert ... on conflict do nothing` and comparing hashes on a conflict.

## Run the tests

```bash
supabase/tests/local/run.sh            # local PostgreSQL 15+ (no Docker): migrations + 80 RLS checks
supabase/tests/local/run.sh --seed     # also loads seed.sql and shows public_stats
deno test --allow-env supabase/functions/eva-chat/handler_test.ts   # eva-chat, offline (fake fetch)
psql "$DATABASE_URL" -f supabase/tests/rls.test.sql                  # against the hosted project (as postgres)
```

## Seed and chain verification

```bash
node supabase/scripts/seed.mjs --verify-dir /tmp/eva-seed     # rewrites seed.sql with a fresh demo key
app/target/release/eva verify --data /tmp/eva-seed            # chain-demo-ship.jsonl: OK · 10 records · 10 Ed25519 signatures valid
```

To check the **cloud copy** without trusting Supabase, export it with a crew lead's token and run the app's verifier:

```bash
SUPABASE_URL=… SUPABASE_ANON_KEY=… EVA_ACCESS_TOKEN=<crew lead JWT> node supabase/scripts/export-chain.mjs --ship demo-ship --out /tmp/eva-cloud
app/target/release/eva verify --data /tmp/eva-cloud
```

## eva-chat

`POST https://<ref>.supabase.co/functions/v1/eva-chat` with `Authorization: Bearer <user access token>` and `{"text": "...", "history": [...], "lang": "en" | "es"}`. Same answers as the site's `/api/eva/chat`: `{text, source: "guard", reason}` or `{text, source: "model", model}`. `401` without a valid JWT, `403` without a profile, `429` + `retry-after` over the per-user limit, `503` if Groq is down. The guard (`guard.ts`) is a copy of `public-sites/api/_lib/guard.ts`; keep them in sync. `GROQ_API_KEY` is a function secret, never in the repo.

## Provisioning

```bash
set -a; . ~/.eva-supabase.env; set +a        # SUPABASE_ACCESS_TOKEN
EVA_SITE_DIR=/path/to/public-sites EVA_VERCEL=/path/to/vercel supabase/scripts/provision.sh
```

Steps: create the project (free) and wait for `ACTIVE_HEALTHY` → store keys → migrations + seed over the session pooler → auth settings → one test user per role → RLS tests → `GROQ_API_KEY` secret + deploy eva-chat + three test questions → `eva verify` on the cloud copy → Vercel env vars, `/status/` page, deploy, secret scan.

Secrets never enter the repo: the DB password, the service-role key and the test users' passwords live only in `/home/user/.eva-supabase-project.env` (chmod 600). The anon key is public by design (RLS protects the data).

## Auth

- Email/password with a confirmed email. Every new account starts as `viewer` (ships and station only, plus Eva's chat); roles change only through `select admin_set_role('<uid>', 'team')` as mission control, or with the service role.
- Site URL `https://eva-wearmeds.vercel.app`; redirects `http://localhost:8080/**` and `https://eva-wearmeds.vercel.app/**`.

### Google sign-in (ready to enable)

Needs an OAuth client from Google Cloud, which only a team member can create:

1. [Google Cloud console](https://console.cloud.google.com/) → *APIs & Services* → *OAuth consent screen*: External, app name "Eva by WearMeds", support email, authorised domain `supabase.co` (and `vercel.app` if asked). Scopes: `openid`, `email`, `profile`.
2. *Credentials* → *Create credentials* → *OAuth client ID* → *Web application*.
   - Authorised JavaScript origins: `https://eva-wearmeds.vercel.app`, `http://localhost:8080`
   - Authorised redirect URI: **`https://<project-ref>.supabase.co/auth/v1/callback`**
3. Supabase dashboard → *Authentication* → *Sign In / Providers* → *Google*: enable, paste the client ID and secret, save. (Or `PATCH /v1/projects/<ref>/config/auth` with `external_google_enabled`, `external_google_client_id`, `external_google_secret`.)

Google accounts arrive verified and start as `viewer`, like any other.

## Not done (needs a paid plan or a later decision)

- Leaked-password protection, custom SMTP (the built-in mailer is rate-limited), PITR backups, and `pg_cron` cleanup of `rate_limits` (call `cleanup_rate_limits()` by hand or enable `pg_cron` on the free plan later).
- Retention (`expireAt` in the Firebase model): not implemented; deleting records would need an audited admin action that lifts the append-only trigger, by design.
