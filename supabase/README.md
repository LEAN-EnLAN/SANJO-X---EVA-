# Eva · Supabase (Earth / cloud side)

Supabase replaces the planned Firebase setup (decision: [`docs/app/ADR-014-supabase.md`](../docs/app/ADR-014-supabase.md)). The ship stays offline-first and never talks to Supabase. Supabase holds a **copy** of what the ground node has already verified and acknowledged, plus team data, and serves Eva's web chat.

## Where it runs: a shared project, schema `eva`

The org's free tier had no slot for a new project, so Eva lives **inside the existing project `changuito`** (ref `rcxmvcxyrwufmoylbrrz`, us-east-1), isolated in its own **`eva` schema**.

> **Status (15/11/2026):** code and tests are ready (86/86 checks pass locally). `provision.sh` has **not** been run on changuito yet: writing to a project another app uses needs the owner's explicit go-ahead.


- every Eva table, view, function, type and trigger is in `eva`; there is **no trigger on `auth.users`** and no event trigger. An Eva profile is created on first use by `eva.ensure_profile()`, so changuito's users get nothing in `eva` unless they use Eva;
- buckets are `eva-team-assets` (private) and `eva-public-media` (public); storage policies are named `eva-…` and each one is scoped to an Eva bucket;
- the Edge Function is `eva-chat`; its Groq key is the secret `EVA_GROQ_API_KEY`;
- migrations are logged in `eva.schema_migrations`, not in the project's `supabase_migrations` (that history belongs to changuito);
- project-wide settings are only **appended** to: `eva` is added to the Data API's exposed schemas, and the Eva URLs are added to the auth redirect allow-list. The Site URL, providers, sign-ups and SMTP stay as changuito set them;
- clients must send the schema header: `Accept-Profile: eva` (reads) and `Content-Profile: eva` (writes, RPC). With supabase-js: `createClient(url, anonKey, { db: { schema: "eva" } })`.

**Never** run `supabase config push`, `db push`, `db reset` or `link` against this project. Moving Eva to its own project later: see ADR-014.

## Layout

| Path | What |
|---|---|
| `migrations/` | SQL migrations, applied in order: schema, roles and profiles · ship data · journal and team · storage · chat rate limit · `public_stats` |
| `tests/rls.test.sql` | RLS, integrity and isolation tests (86 checks), one transaction, always rolled back |
| `tests/local/` | Run the migrations and tests on a throwaway local PostgreSQL without Docker |
| `functions/eva-chat/` | Edge Function (Deno): JWT check, first-use profile, per-user rate limit, the app's topic guard, Groq |
| `seed.sql` | Demo data (fictional, from `app/src/seed.rs`), generated by `scripts/seed.mjs` |
| `scripts/seed.mjs` | Builds `seed.sql` with hash-chained, Ed25519-signed records (same hashing as `app/src/chain.rs`) |
| `scripts/export-chain.mjs` | Exports a ship's mirrored records to the app's chain format for `eva verify` |
| `scripts/sql.sh` | Runs SQL (or the RLS test) on the hosted project through the Management API, no DB password needed |
| `scripts/provision.sh` | Inspects the project, refuses name collisions, then sets Eva up end to end (idempotent, prints no secrets) |
| `site/` | `/status/` page and `/api/status` route for the public site (copied there by `provision.sh`) |
| `config.toml` | Supabase CLI config, only for `functions deploy eva-chat` |

## Data model

Translated from the Firebase kit's `DATA-MODEL.md` and `firestore.rules`. All tables are in `eva`.

| Table | Contents | Written by |
|---|---|---|
| `profiles` | One per Eva user, created by `ensure_profile()` on first use: `display_name`, `email`, `prefs`, `role` (`crew_lead` · `mission_control` · `team` · `viewer`, default `viewer`) | owner (`display_name`, `prefs` only); `role` only by `admin_set_role()` or the service role, audited in `role_changes` |
| `ships` | Ship summary, `demo` flag, pinned Ed25519 `pubkey` (immutable), `epoch` (only moves forward), head | service role; mission control may edit `display_name`, `notes` |
| `records` | Signed chain mirror: `ship, epoch, seq, ts, kind, subject, hash, prev, signature, body` (+ `ground_received_ms`, `ingested_at`). PK `(ship, epoch, seq)` | **service role only, append-only**: triggers refuse UPDATE, DELETE and TRUNCATE for everyone; an insert must link to the previous record's hash (and seq 0 to genesis) |
| `cases`, `case_notes` | Cases rebuilt by the ground; helpers by seat and task, never names. Notes are append-only | service role; notes by mission control / crew lead |
| `passengers` | Triage summary only: `seat, label ("Ana R."), role, trained, grp, status` | service role. Checks refuse full names and free text in `status`; the test refuses any extra (vitals-like) column |
| `station_state` | Medical station: mode, 12 compartments. No health data | service role |
| `journal_entries` | Private per user | owner only (nobody else, not even mission control, can read them) |
| `team_docs` | Reports, notes, asset metadata | team, mission control (author or mission control edit / delete) |
| `rate_limits` | eva-chat buckets (6 / min, 80 / day) | only through `eva_chat_consume()` |
| `public_stats` (view) | Per ship: acknowledged record count, last ingest, open / total cases, passenger count, station mode | read by `anon` (the `/status/` page) |

No Eva foreign key or trigger can block deleting an auth user of the host app: profiles, journals and rate limits cascade, team docs set the author to null, and case notes keep the author id without a foreign key.

The ground node's ingest (later, `app/src/cloud.rs` as in the Firebase kit's INTEGRATION.md, part A) writes with the service role and `Content-Profile: eva`, using `insert … on conflict do nothing` and comparing hashes on a conflict.

## Run the tests

```bash
supabase/tests/local/run.sh            # local PostgreSQL 15+ (no Docker): migrations + 86 checks
supabase/tests/local/run.sh --seed     # also loads seed.sql and shows eva.public_stats
deno test --allow-env supabase/functions/eva-chat/handler_test.ts   # eva-chat, offline (fake fetch)
SUPABASE_ACCESS_TOKEN=… supabase/scripts/sql.sh --rls-test          # hosted project (needs the eva-test users)
```

The hosted test never writes `auth.users`: it uses the `eva-test-*` users that `provision.sh` creates, and ends with a RAISE that carries the results and rolls back everything.

## Seed and chain verification

```bash
node supabase/scripts/seed.mjs --verify-dir /tmp/eva-seed     # rewrites seed.sql with a fresh demo key
app/target/release/eva verify --data /tmp/eva-seed            # chain-demo-ship.jsonl: OK · 10 records · 10 Ed25519 signatures valid
```

To check the **cloud copy** without trusting Supabase, export it with a crew lead's token and run the app's verifier:

```bash
SUPABASE_URL=… SUPABASE_ANON_KEY=… EVA_ACCESS_TOKEN=<crew lead JWT> node supabase/scripts/export-chain.mjs --ship demo-ship --out /tmp/eva-cloud
app/target/release/eva verify --data /tmp/eva-cloud
```

## eva-chat

`POST https://<ref>.supabase.co/functions/v1/eva-chat` with `Authorization: Bearer <user access token>` and `{"text": "...", "history": [...], "lang": "en" | "es"}`. Same answers as the site's `/api/eva/chat`: `{text, source: "guard", reason}` or `{text, source: "model", model}`. `401` without a valid JWT, `403` without a role, `429` + `retry-after` over the per-user limit, `503` if Groq is down. The first message creates the caller's Eva profile (`viewer`). The guard (`guard.ts`) is a copy of `public-sites/api/_lib/guard.ts`; keep them in sync. `EVA_GROQ_API_KEY` is a function secret, never in the repo.

## Provisioning

```bash
set -a; . ~/.eva-supabase.env; set +a        # SUPABASE_ACCESS_TOKEN
EVA_SITE_DIR=/path/to/public-sites EVA_VERCEL=/path/to/vercel supabase/scripts/provision.sh
```

Steps: 0 inspect (schemas, functions, buckets, storage policy names, secret names) and stop on any collision · 1 keys (anon to the secrets file; the service-role key stays in memory) · 2 migrations · 3 append `eva` to the exposed schemas · 4 seed · 5 append the redirect URLs · 6 `eva-test-*` users and their `eva.profiles` roles · 7 RLS tests · 8 `EVA_GROQ_API_KEY` + deploy eva-chat + three test questions · 9 `eva verify` on the cloud copy · 10 Vercel env vars, `/status/` page, deploy, secret scan.

Secrets never enter the repo: the anon key, the URL and the test users' passwords live in `/home/user/.eva-supabase-project.env` (chmod 600). The anon key is public by design (RLS protects the data).

## Auth

- The project's auth settings belong to changuito and are not changed (email/password and Google are already on there). Any signed-in user of the project gets an Eva `viewer` profile the first time they use Eva; roles change only through `select eva.admin_set_role('<uid>', 'team')` as mission control, or with the service role.
- Eva adds `https://eva-wearmeds.vercel.app`, `http://localhost:8080` (and their `/**` paths) to the redirect allow-list.
- Google sign-in uses the project's existing Google provider (configured by changuito). With a dedicated project, set up an OAuth web client whose redirect URI is `https://<ref>.supabase.co/auth/v1/callback`, then enable Google under *Authentication → Sign In / Providers*.

## Not done

- Leaked-password protection, custom SMTP, PITR backups and `pg_cron` cleanup of `rate_limits` (call `eva.cleanup_rate_limits()` by hand): free plan, and project-wide settings that belong to changuito.
- Retention (`expireAt` in the Firebase model): not implemented; deleting records would need an audited admin action that lifts the append-only trigger, by design.
